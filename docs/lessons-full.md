# Lessons, in full

## 2026-11-06 multiCMD: a command that differs from another only in case is a script file, not an entry point
- Changed: `multiCMD` is no longer a console entry point: `setup.py` installs it as the script file `scripts/multiCMD` (`scripts=`), and `mcmd` and `multicmd` stay entry points. All three are still commands and print the same version.
- Why we had to change: pip 9.0.3, the pip of EL7 and EL8, reads `entry_points.txt` with a case-folding config parser. With `multiCMD` and `multicmd` in it, `pip3 install -U multiCMD` and `pip3 uninstall multiCMD` stopped with `configparser.DuplicateOptionError`.
- Original design was wrong because: it took a command name for a file name only, where a case-sensitive file system keeps `multiCMD` and `multicmd` apart, and not for the key of a config file that a different tool reads on uninstall.
- Lesson: no two commands in one `entry_points.txt` may differ only in case. Install, upgrade and uninstall with the stock pip of the oldest platform the package supports before a release.

## 2026-11-10 multiCMD: a child that runs code before its exec waits for its parent's go-ahead
- Changed: on Python 3.6 to 3.10 the exec wrapper takes the read end of a pipe as its second argument (`-c CODE COUNT FD COMMAND...`, passed to it alone) and runs the command only after reading one byte from it; `_popen` writes that byte once the command is in `started`, and closes both ends however `Popen` ends. A wrapper that reads the end of the pipe instead exits 125 without running anything. The approved known limitation "A Ctrl-C inside Popen during a serial start can orphan the command" now covers Python 3.11+ and Windows only.
- Why we had to change: a Ctrl-C (or a SIGTERM handler's `SystemExit`) that Python raised inside `Popen` once it had forked lost the command: it ran on in a process group of its own, unknown to `kill_all()`. 1.56 measured the window at about 51 µs per start on Python 3.14 and approved it. On Python 3.6 a start of a large program spends about 2.5 ms in `Popen` (the fork, then the wait for the wrapper's exec), a fifth of a busy hpcp copy worker's time: hpcp's early-stop test ran 66 lost `cp` commands in 200 stops on 3.6 and 33 in 200 on 3.10.
- Original design was wrong because: it measured the window on one Python, in a small program, and took it as one that "cannot be closed from Python". That holds for the fork's own C call, but the wrapper's child runs code before the command's exec and can wait there. The two fixes tried before do not work: blocking the stops with `pthread_sigmask` in the calling thread lets another thread take the signal while Python still raises it on the main thread (checked on 3.6, 3.12 and 3.14), and holding the Python handlers (1.56's `_HoldCtrlC`) drops C-level handlers, keeps a Ctrl-C waiting on an exec that cannot finish, and turns a missing command's 127 into a stop.
- Lesson: when a start can be cut short between the fork and the hand-over to the caller, and the child runs code before its exec, have the child wait for a go-ahead byte on a pipe from the parent; EOF means "you were never handed over, run nothing". Measure a race's window on the oldest and slowest platform supported, inside the real program.

## 2026-11-10 multiCMD: start threads where no signal handler runs
- Changed: a command's output readers are `_Reader`s, threads started by one C call (`_thread.start_new_thread`), so they are not in `threading.enumerate()` or `threading.active_count()` and `threading`'s trace, profile and excepthook do not reach them. Every other thread multiCMD starts on the main thread (a pool's workers, fire-and-forget commands, an `AsyncExecutor`'s dispatcher) has `threading.Thread.start()` run on a helper thread, itself started by one C call, while the caller waits on a `_Done`; an interrupt there waits for the helper (1 s at most) before it is raised, so the thread's `_started` says whether it runs. The conversion of `RuntimeError('release unlocked lock')` back into the Ctrl-C it hid is gone with its cause.
- Why we had to change: Python runs a signal's handler on the main thread only. One that raised inside `threading.Thread.start()` there, after `with _active_limbo_lock:` had taken the lock but before the block's exit was armed, or in the wait for the new thread's `_started` Event, left that lock held: every later thread start in the program blocked, and on Python 3.6 its exit too. A serial run starts two readers per command on the main thread, so a program stopped often met it: a probe that stops serial commands at random hung 6 of 6 runs of 20,000 calls on 3.14 with 1.59 (after 30 to 9,000 calls: the plan's three runs after 30, 130 and 1,800, the build's three after 4,690, 5,300 and 9,000; py-spy showed the readers waiting for that lock), and hpcp's 9.87 re-review saw a copy hang so.
- Original design was wrong because: it took `threading.Thread.start()` for a call, where it is Python code that takes a lock with `with` and waits on an Event in the calling thread, and on the main thread a Ctrl-C can land anywhere in it. 1.56 guarded what `start()` raised (the RuntimeError conversion), not what it left held. Blocking SIGINT in the calling thread would not hold it while another thread exists (1.59's lesson).
- Lesson: on the main thread of a program a Ctrl-C can interrupt, start threads where no handler runs: with `_thread.start_new_thread`, one C call, or by running `threading.Thread.start()` on a helper made by that call, and store what the C call made before Python can raise (`list.extend(map(...))`), so an interrupt that lands meanwhile knows whether the thread runs.

## 2026-11-10 multiCMD: the embed decodes with zlib, not lzma
- Changed: `compressedEmbeddedCodeGenerator.py` compresses with zlib and writes `multiCMD_min_zlib_a85.py`, whose block begins `import sys,types,base64,zlib`; `multiCMD_min_lzma_a85.py` is gone. Programs that paste the block (hpcp, statblk, statbtrfs) take the new file at their next version.
- Why we had to change: the lzma block made a program that pasted it fail to import on a Python built without `_lzma` (a pyenv or source build on a host without the xz headers, common on HPC hosts) whenever its installed multiCMD was older than the block's gate, or missing; each new gate reached more installs.
- Original design was wrong because: it chose the codec by size alone (lzma's text is about 7 % smaller here) and took an optional module for one every Python has.
- Lesson: code embedded for any Python decodes with what every target has: zlib, which pip itself needs, not lzma.

## 2026-11-11 multiCMD: a helper Python starts with SIGINT blocked
- Changed: on Python 3.6 to 3.10 the exec wrapper starts with SIGINT blocked: `_spawn_process` adds SIGINT to the signals it blocks in the calling thread for the start, which the wrapper inherits, unless that thread has SIGINT blocked already. The hand-over byte says which: `b'2'` has the wrapper set SIGINT back to its default (unless it is ignored) and unblock it once it has read the byte, `b'1'` leaves the mask as it is. A command so inherits SIGINT unblocked, or blocked from a calling thread that blocks it, as before.
- Why we had to change: a stop sends SIGINT first, 10 ms before SIGTERM. One that reached the wrapper's Python while it initialized aborted it with a core dump on 3.6 and 3.7 ("Fatal Python error: Py_Initialize: can't initialize sys standard streams", 80 and 63 of 400 stops aimed into a start) and ended it with that message and 1 on 3.8 to 3.10 (41 to 54 of 400); a little later it printed a `KeyboardInterrupt` traceback. The text landed in the command's stderr, and each core dump in the host's crash handler: on a GitHub runner, 1.60's new stop test (5,000 stops of `true` in one process) started an apport for each, drove the load to 250, timed the 3.6 job out in one run and failed five timing tests after it in the rerun. On our host (`core_pattern` = `core`) the same dumps cost a file write each, so the tests passed here.
- Original design was wrong because: it took the wrapper for code that runs from its first line, where a stop can reach the interpreter before any of that code runs, and the interpreter's own SIGINT handler is in place by then. 1.59's lesson (a child that runs code before its exec waits for its parent's go-ahead) covered a stop in the parent, not one sent to the child.
- Lesson: a program that may stop a Python child it just started, with SIGINT first, starts it with SIGINT blocked (the signal mask survives fork and exec) and has the child unblock SIGINT once it can be stopped cleanly. When a test is slow only on CI, look at the whole host (load, the processes that use the CPU) before the code: here the cost was in the crash handler, not in the program.
